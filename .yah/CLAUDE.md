# yah session host

This file is managed by yah; the content is truly-global across all
jobs and sessions in this camp. Per-session and per-job content is
injected via `--append-system-prompt` at process spawn instead of by
rewriting this file (R268 race fix).

## Environment quirks

- **`mcp__yah__ask_user`** is the canonical user-choice affordance: use it for structured multiple-choice prompts (multi-option, multi-select, or multi-question forms). Do NOT use it for single free-form questions — just print those into chat. `AskUserQuestion` is not wired up in this host.
- **Tool-use approvals** (Bash, Write, etc.) that claude-cli would ask about route through the AnswerQueue UI via the `yah-gate` tool.check mod; a Continue/Revise modal will appear in the desktop panel. To minimize Revise round-trips: name the target in the call's `description` ("Read app/yah/cli/src/main.rs" beats "Read file" — the user pattern-matches on description before clicking Continue); scope paths narrowly (`rg "foo" crates/yah/board/` is approvable, unbounded `rg "foo"` is a Revise); don't pre-stage destructive shapes (`rm -rf`, `git reset --hard`, `find … -delete`, `--no-verify`) unless the user has authorized that exact operation — they escalate to a hard review even when the target is harmless.
- **Grep `type: "tsx"` returns zero results silently.** claude-cli's Grep wraps ripgrep, which only knows `ts` (covers `.ts` and `.tsx`). Use `type: "ts"` or `glob: "**/*.tsx"`. If a Grep you expect to match returns nothing, recheck the type field before concluding the pattern is absent.
- **A repo-wide search gets truncated by `@yah:` annotation prose, silently and in the clean-looking direction.** The board lives in doc comments, so the hottest files are mostly annotation text — measured 2026-09-13: `app/yah/cli/src/camp.rs` is 4,528 doc-comment lines of 38,270, `oss/yubaba/crates/cloud/src/lib.rs` is 283 of 361. A single annotation line runs past 1 KB, so a dozen prose hits exhaust the 32 KB tool-output cap and the *code* hits scroll off the end. That is not hypothetical: a pre-deletion sweep for `legacy_services` read clean while four `E0560` call sites survived, and `cargo check -p yah` stayed red camp-wide for ~50 minutes (R901-B1). So **an empty or tidy-looking sweep is the least trustworthy result you can get here.** Confirm it twice: drop the prose with `grep -vE '(^|:)[0-9]+:[[:space:]]*(//|\*)'` (strips `///`, `//!`, and `/*` block comments from both single-file and multi-file grep output, regardless of filename prefix; including indented ones; the old rg pattern failed on indented comments inside impl blocks), and get the count from `| wc -l`, which no output cap can truncate.
- **A piped command's exit code is the LAST stage's, so `cargo … | tail` reports `tail`'s 0 on a failed build** — and that 0 is what the task notification shows you. Nothing is lying; the shell answered the question it was actually asked. Relocated builds are now immune (camp-service runs `build-run` origin lines under `pipefail`, R901-B2), but **your own Bash tool is not**, and `echo "EXIT=${PIPESTATUS[0]}"` does not rescue it here: this host's Bash tool is **zsh**, which has no `PIPESTATUS` at all, so that idiom expands to the empty string and prints `EXIT=` however the build went. zsh spells it `$pipestatus[1]` (arrays are 1-indexed). Simplest thing that is right in both shells: put `set -o pipefail;` in front of the line. Separately, a backgrounded build can be reported as "ended, exit code 0" with an EMPTY output file while cargo is still alive and blocked on the build-directory lock — that number is the watcher's quiet-window rule, not the run's. When a build's verdict matters, make it durable: `cargo … > /tmp/x1.log 2>&1; echo "EXIT=$?" >> /tmp/x1.log`, then read the file — and **type a fresh literal path every attempt**. That is not fussiness (R913-B8): the quiet window above makes you believe run 1 ended and re-arm run 2 onto the same log, the `cargo-target` key serialises only the cargo invocation and not the `rm`/`echo`/`grep` around it, so your `grep` matches a `test result` line the OTHER run produced — a clean-looking *positive*, which nothing downstream can tell from a real one. `yah build run` now refuses a second run writing a live run's redirect target and names whose session holds it, but it reads the path off the command's AST, so `> "$LOG"` hides the collision from the one check that would have caught it.
- **`rg` is a claude-cli shell function, not a binary, so it does not exist outside your own Bash tool.** It comes from `~/.claude/shell-snapshots/snapshot-zsh-*.sh` and re-execs the claude binary as `ARGV0=rg`. Nothing else on the box sources that snapshot — the camp daemon's build shell (`sh -c`, where a relocated `cargo … | rg …` actually runs), a QED step, a git hook, a `scripts/*.sh`, a codex/kimi session. There, `rg` is exit 127, which `||` cannot tell apart from exit 1 — so the very common `rg <pat> <path> || echo "(none)"` prints its clean-looking fallback **because the binary was missing**, and a fabricated "zero matches" gets written onto a ticket as measured evidence (R901-B3). A real ripgrep was installed at `/opt/homebrew/bin/rg` on 2026-09-13 so both surfaces now agree, but that is one machine's state and does not travel: off your own Bash tool, reach for `grep -rn --include='*.rs'`, and never let `|| echo none` stand as proof. The general rule these three bullets share: **a clean-looking negative is the least trustworthy result in this camp.** Before a sweep counts as evidence that a deletion or migration is complete, confirm the tool ran, the output was not truncated, and the exit code came from the command you think it did.

## What yah's own nouns mean

yah's vocabulary is used far more than it is defined, so a confident reading of one is often a guess wearing a local accent — **`QED` is yah's CI layer, emphatically not "proven"**. Two read-only verbs, neither costing anything until called: `party.load {"ids": ["glossary"]}` defines the domain nouns (qed, camp vs rig, relay, sigil, divination, almanac, yubaba, kamaji, gnome, courier, and each `oss/` project); `party.search_doctrine {"needle": "<term>"}` returns every line of doctrine this camp can hand a session that uses the term, labelled with where it came from. A term absent from both is one yah has not defined — say so rather than inventing a meaning.

## Inspecting live agents

To see the realtime state of every character in this camp — each non-dormant slot's phase (its 'life'), which camp and session it is on, turns, and currently-used context — call `camp.roster` for a one-call snapshot. The granular peers are `camp.sessions` (live session list), `camp.slots` (slot occupancy), and `party.agent_status` (one session's context + cumulative token spend). All are read-only; if they are not already in your tool list, ToolSearch for them by name.

**`camp.roster` is scoped to THIS camp, and that matters the moment you measure anything.** A sibling camp under the same `yah.app` daemon is structurally invisible to it, so a loud machine reads as a quiet camp — measured 2026-08-29, when the roster reported a quiet camp while `~/ss/noisetable` was running a release build on the same cores, and every wall-clock number taken that day was contaminated. Before ANY timing sample (a build, a benchmark, a cache hit rate), call **`camp.machine`** instead: one machine-wide call listing every camp on the box with its live slots, the rustc/cargo process census, load average, and the shared sccache dir. Read its `quiet` field — it is true only when nothing foreign is live AND the compile census read zero AND the census was actually readable, so a check that could not look reports `quiet: false` rather than a false all-clear. Do not hand-roll the process check: `pgrep -c` does not exist on macOS — it exits 2 with a usage error that a shell `if` reads as quiet — and bare `pgrep rustc` under-reports, since an sccache hit runs no rustc at all and the cargo driver is invisible to it. The spelling that sees both halves is `pgrep -l "rustc|cargo"`. (Until 2026-09-11 `pgrep rustc` returned 0 during *every* build here, because `cargo-orphan-gc` held the `rustc-wrapper` slot and owned `argv[0]`. That wrapper is retired — R888-T1 — so rustc runs under its own name again; `pgrep -f cargo-orphan-gc`, which older notes recommend as the cross-check, now matches nothing during the busiest build on the machine.)
